# KICC EasyPay 일반결제 연동 안내

이 구현은 **KICC EasyPay 일반결제의 통합형 Hosted Web 결제창**을 사용한다. 고객의 카드번호, CVC, 빌링키, `customerKey`, `easypayVirtualNo`를 브라우저나 서버에 받거나 저장하지 않는다. 거래등록 응답의 `authPageUrl`을 브라우저에서 열고, 인증 뒤 `returnUrl`로 받은 `authorizationId`만 서버가 승인 API에 보낸다.[1] [2] 이는 등록된 카드나 가상카드번호로 과금하는 간편결제 API가 아니다.

## 배포 설정

운영 서버의 비밀 환경변수에만 다음 네 값을 둔다. `WILLCLUB_EASYPAY_ENABLED`가 정확히 `true`이고 나머지 세 값이 모두 유효할 때만 카드 주문 생성 및 등록이 활성화된다. API 요청에 별도 API key를 넣지 않는다. KICC 일반결제 문서는 `mallId`와 승인 응답 `msgAuthValue` 검증에 쓰는 Secret Key를 요구한다.[3]

```text
WILLCLUB_EASYPAY_ENABLED=true
WILLCLUB_EASYPAY_MALL_ID=<KICC가 발급한 8-byte 상점ID>
WILLCLUB_EASYPAY_SECRET=<KICC 영업 담당자가 제공한 Secret Key>
WILLCLUB_EASYPAY_API_DOMAIN=https://testpgapi.easypay.co.kr
# 상용 전환 시: https://pgapi.easypay.co.kr
# 선택: WILLCLUB_EASYPAY_DEVICE_TYPE=pc  # mobile도 가능
```

`WILLCLUB_EASYPAY_API_DOMAIN`은 위 KICC 개발/상용 도메인만 허용한다.[4] URL에 자격증명을 넣지 말고, Secret Key를 프런트엔드 환경변수·로그·오류 응답·Git에 넣지 않는다. 상점의 공개 HTTPS 주소와 `siteOrigin`도 KICC에 등록되어야 하며, `returnUrl`은 KICC가 요구하는 256 byte 이내 주소여야 한다.[2]

## 서버 결제 흐름

각 서버 생성 카드 분할 시도에는 고유한 `serverRef`가 있다. 어댑터는 이를 KICC의 `shopOrderNo`와 `shopTransactionId`로 사용한다. 따라서 VIP 다중카드 결제도 카드별 KICC 주문번호가 충돌하지 않는다. 영상 단일카드, 영상의 포인트 혼합 카드 부분, 포인트 충전, VIP 단일카드 및 2~5장 VIP 다중카드는 모두 이 같은 결제창 흐름을 사용한다. 주문 금액과 카드별 분할 금액은 항상 서버 주문 상태의 canonical 금액이며 브라우저 입력값을 믿지 않는다.

1. 서버는 `POST https://{API Domain}/api/ep9/trades/webpay`에 `mallId`, 고유 `shopOrderNo`, `amount`, `payMethodTypeCode: "00"`, `currency: "00"`, `returnUrl`, `deviceTypeCode`, `clientTypeCode: "00"`, `orderInfo.goodsName`만 JSON/UTF-8로 전송한다. `"00"`과 `clientTypeCode: "00"`은 통합형 결제창 설정이다.[2]
2. 응답 `resCd: "0000"`의 `authPageUrl`만 브라우저에 반환한다. 고객이 그 KICC 결제창에서 카드/허용된 결제수단을 선택하고 인증한다.
3. 어댑터는 `returnUrl`에 서버가 만든 불투명 `callbackToken` 쿼리를 붙인다. KICC는 해당 URL에 URL-encoded POST로 `resCd`, `shopOrderNo`, `authorizationId`를 전달한다.[1] [5] 라우터는 토큰으로 저장된 시도를 찾고, 콜백 `shopOrderNo`가 그 시도의 `serverRef`와 같은지 확인한다. 콜백의 주문 ID, 성공 문구, 카드 값은 상태 변경 근거가 아니다.
4. 인증 콜백의 `resCd`가 성공이어도 서버는 `POST https://{API Domain}/api/ep9/trades/approval`을 호출한다. 요청은 `mallId`, 동일한 `shopOrderNo`, `shopTransactionId`, 원문 그대로의 `authorizationId`, 당일 `approvalReqDate`다.[3]
5. 서버는 승인 응답의 `resCd`, `mallId`, 두 KICC 식별자, canonical 카드부분 금액, `pgCno`, 그리고 `HMAC-SHA256(pgCno|amount|transactionDate)`를 Secret Key로 모두 검증한다.[3] 이 검증 뒤에만 내부 주문 엔진에 `KRW` 승인 결과를 전달하고, 모든 카드 부분 승인 후에만 영상 이용권·VIP 서비스·유료 포인트를 기록한다. 카드 마스킹 번호를 포함한 원시 PG 응답은 저장하지 않는다.

인증 실패 `resCd`는 결제 실패로 기록한다. 통신 타임아웃, 연결 실패, HTTP/JSON 응답 불명확 상태는 `PG_RECONCILIATION_REQUIRED`로 남기며 실패나 성공으로 임의 기록하지 않는다. KICC는 이 경우 거래상태를 조회하고 유효한 PG 거래번호가 있으면 취소하도록 안내한다.[3] 이 모듈의 `cancel()`은 의도적으로 자동 취소하지 않으며 항상 관리자 확인 절차를 요구한다.

## 라우터 계약과 안전 경계

브라우저의 주문 생성과 결제창 등록 `POST`는 로그인 세션, 허용 Origin, CSRF 토큰이 필요하다. 공개 `POST /api/payments/easypay/return`은 KICC의 결제창이 세션 쿠키 없이 호출할 수 있는 유일한 예외다. 이 경로는 `callbackToken` 쿼리와 KICC 본문의 `shopOrderNo`/`authorizationId`를 받는다. 호환을 위해 이전 내부 호출의 본문 `callbackToken` 및 `shopTransactionId`도 토큰과 일치할 때만 허용하지만, 일반결제 신규 연동은 공식 콜백 필드를 사용해야 한다.

`POST /api/payments/orders/:id/parts/:partId/register`의 성공 응답은 `{ url, part }`이며 `url`은 KICC hosted checkout 주소다. 결제 성공 페이지로의 303 이동은 서버 승인과 내부 CAS 상태 반영을 마친 뒤에만 일어난다. 다중카드 중 일부만 승인되면 자동 환불 성공으로 가장하지 않고 `manualrefund_required`로 처리한다.

## 서버 장착 예시

```js
import { loadPaymentConfig } from './easypay-provider.mjs';
import { createPaymentRouter } from './payment-router.mjs';

app.use('/api/payments', createPaymentRouter({
  store,
  authConfig: config.auth,
  siteOrigin: config.siteOrigin,
  config: loadPaymentConfig(process.env),
}));
```
